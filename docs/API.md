# Portfolio API v1

Base URL: `https://YOUR_DOMAIN`. All requests/responses are JSON unless a file upload or media stream is noted. These routes are served by `src/index.js`.

## Authentication

Every `/api/admin/*` call requires `Authorization: Bearer YOUR_32_BYTE_RANDOM_TOKEN`. This token is generated by `scripts/deploy.sh`, saved only in `.secrets/admin-token.txt` on your own machine, and installed as a Worker secret. The dashboard keeps it in JavaScript **memory**, not localStorage, cookies, or sessionStorage. A browser reload loses it. Admin APIs reject unauthenticated requests, even if the admin HTML can be opened.

Non-browser clients (curl, scripts, AI agents) can call the API with a token. Browser frontends on another origin need their exact origin in `ALLOWED_ORIGINS`, e.g. `http://localhost:3000`. **Don't enable `*` for bearer-authenticated endpoints.**

Admin token examples (avoid typing secrets into your shell history):

```bash
read -rsp 'Admin token: ' TOKEN; echo
curl -fsS https://YOUR_DOMAIN/api/admin/state -H "Authorization: Bearer $TOKEN"
unset TOKEN
```

Collections: `projects`, `experience`, `socials`, `views`, `hardSkills`, `softSkills`, `certificates`, `offers`, `customSections`, `media`.

### Examples

Create/update a project by ID (a project can belong to multiple tracks):

```bash
curl -fsS -X PUT 'https://YOUR_DOMAIN/api/admin/collections/projects/shop-platform' \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data '{"id":"shop-platform","title":"Shop platform","summary":"A live commerce project","tracks":["Backend","Full-stack"],"stack":["Node.js","PostgreSQL"],"published":true,"featured":true,"mediaIds":[]}'
```

Upload a PNG and get its media ID and public URL:

```bash
curl -fsS -X POST 'https://YOUR_DOMAIN/api/admin/files?name=cover.png' \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: image/png' \
  --data-binary @cover.png
# -> {"id":"UUID", "src":"/media/UUID", ...}
```

Upload the CV:

```bash
curl -fsS -X PUT 'https://YOUR_DOMAIN/api/admin/cv' \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/pdf' \
  --data-binary @MyCV.pdf
```

Create a contact message:

```bash
curl -fsS -X POST 'https://YOUR_DOMAIN/api/contact' \
  -H 'Content-Type: application/json' \
  --data '{"name":"Visitor","email":"visitor@example.org","message":"I would like to discuss a project."}'
```

Successful uploads use HTTP `201`; unauthorized uses `401`; disallowed origins use `403`; invalid requests use `400` or `415`; missing upload length uses `411`; upload over-limit uses `413`; unrecognized routes use `404`; referenced media deletion uses `409`; unsatisfiable byte ranges use `416`; repeated wrong tokens and excessive contacts may use `429`.

### Current API contracts

**Media.** Supported upload MIME types: `image/png`, `image/jpeg`, `image/webp`, `image/gif`, `image/avif`, `video/mp4`, `video/webm`, `application/pdf`, `application/json`, `text/plain`. Send the raw file, not multipart or base64; use a known length and URL-encode the filename. The generic upload returns `{id,name,type,src,bytes}` and creates the R2 object plus its SQL record; register the returned item in the CMS `media` collection before attaching it. The portrait endpoint does this registration itself. Rename via PATCH, not collection replacement: the name is limited to 180 characters, cannot contain path separators/control characters, and must preserve the extension. The original `/media/:id` URL does not change. Image/video conversion, crop and scale are performed by Media Studio in the browser, not by an HTTP conversion endpoint. Edited copies use new media IDs.

Before deleting media, read `/api/admin/files/:id/references`. If `used` is true, stop and report the references, including drafts. The delete route also checks references server-side and returns 409 if still used. Do not bypass it with collection deletion. Media URLs are public by ID, including assets attached to drafts; unpublished project text is protected, but an unlisted asset URL is not an authorization boundary. Never upload confidential assets assuming a draft makes them private.

`HEAD /media/:id` returns metadata including `Content-Length` and `Accept-Ranges: bytes`. A valid single `Range: bytes=0-1023`, open-ended range or suffix range returns 206 with `Content-Range`; an invalid/unsatisfiable range returns 416. A full GET returns 200. `If-Range` may cause a full response if the ETag does not match. Native players can request the byte ranges needed for seeking; the browser controls buffering.

**Contact and messages.** Contact JSON requires `name` (at least two characters), `message` (at least eight), and either `contactMethod: "email"` (default) with valid `email`, or `contactMethod: "whatsapp"` / `"telegram"` with valid `phone` and ISO `country` for local numbers. `website` is a honeypot. The inbox may contain private IP/contact information; do not export, disclose or delete it without authorization. PATCH accepts either or both boolean fields `read` and `archived`; omission of both is invalid.

**CVs.** `PUT /api/admin/cv` is the legacy single-CV route. For named CVs, upload a PDF via the generic files API, register the returned media item, and update `settings.cvs` in a freshly fetched CMS snapshot with entries `{id,title,mediaId}` (preserve existing properties and entries). `/cv/:id` uses the entry ID, not the media ID.

**Full SQL backup.** `GET /api/admin/export?parts=database` requires the admin bearer token and downloads a `.sql` file (`application/sql`). `parts=database,media` downloads a TAR containing `backup.sql` and registered original R2 files at their original `media/<uuid>.<ext>` keys. The old JSON selections are no longer accepted. The SQL is generated from the live SQLite schema, includes all application tables (including drafts, messages, message_details, message_countries, analytics, rate-limit records and migration records if present), explicit indexes, views, triggers, and autoincrement sequences. Cloudflare-managed `_cf_*` and SQLite internal metadata tables are excluded; Worker secrets and external Cloudflare analytics are not database rows. Table dependencies are read from foreign keys and parent tables/rows precede dependent ones where possible; checks are deferred for D1 import. Values are encoded by SQLite to preserve text, BLOBs and large integers. SQL is limited to 32 MiB; use Wrangler native D1 export for larger databases or unsupported virtual tables. D1 table reads are batched; schema changes during export cause failure, but D1 and R2 are not one atomic snapshot. Restore into a fresh SQLite/D1 database, not an existing populated one, and verify `PRAGMA foreign_key_check;`. SQL contains no explicit BEGIN/COMMIT for D1 compatibility. For local SQLite: `sqlite3 -bail restored.db < backup.sql`; for a new D1 database: `npx wrangler d1 execute NEW_DATABASE --remote --file=backup.sql`. Restore archived R2 files separately using their exact object keys and the recorded MIME types. No automatic restore endpoint exists. `Content-Disposition` and `X-Export-Bytes` identify the download; cache is private/no-store. Keep backups private: they include contact data and IP-related records.

```bash
curl --fail-with-body -H "Authorization: Bearer $TOKEN" \
  'https://YOUR_DOMAIN/api/admin/export?parts=database,media' \
  --output portfolio-backup.tar
```

### Notes

- After **each** admin update the browser sends the bearer token. Opening `/admin` without a token only renders the login form; it never authorizes APIs.
- Changes made through the collection endpoints are visible after a full dashboard refresh/unlock.
- State snapshot and collection endpoints validate required fields and IDs. The serialized snapshot is limited to 900,000 characters; `putState` also rejects more than 220 batched statements. Collection writes currently call `putState` too, so they do not bypass this limit. Put all binary content in R2.
- Media URLs identify immutable objects; replacing a photo means uploading a new media ID and updating its reference. The draft preview runs inside the authenticated admin page; there is no public draft preview endpoint.
- D1 traffic metrics are *pageview events*, not unique people, sessions or time-on-page. They may include bot traffic. Country is based on Cloudflare geolocation. Time is in UTC, not Cairo. Cloudflare GraphQL zone HTTP request totals may include other traffic on the same domain.
- API calls to protected endpoints from a different **browser origin** require setting `ALLOWED_ORIGINS` in `wrangler.jsonc` and redeploying. API tools/scripts normally send no browser Origin and do not require CORS.

## Project cover, multiple areas and clear editing fields (V7)

Each project is stored as a JSON document in D1. **No new D1 migration is required** for these fields.

- `coverMediaId`: optional R2 media ID (not the URL) of the dedicated image used on homepage project cards. The public server-rendered HTML and browser render both use it. If absent, the first gallery image is used; if neither exists, a plain blue abstract background appears **without project initials**.
- `mediaIds`: optional array of image/video IDs for the project gallery. A cover does **not** need to be included in the gallery.
- `tracks`: array of one or more area tags, e.g. `["Backend", "AI Integration", "Frontend"]`. Tags are not exclusive; a project may appear in more than one category and focused share link. Categories originate from project tags (no separate category table).
- `role`: a short description of personal responsibility, e.g. `Backend Development · AI Integration`. It is not an exhaustive essay.
- `summary`: 1–2 sentences for project cards / search meta description.
- `overview`: what the project does, for whom, and overall scope.
- `problem`: real challenge or problem; `solution`: how you addressed it.
- `features` (`featuresAr`, `featuresEs`): displayed under **Highlights**. Short, concrete, true statements.
- `featured`: prioritize project in the homepage's selected-work list; visibility is controlled separately by `published`.

Upload/attach cover in two steps (or use `python3 scripts/portfolio_agent.py upload --file cover.webp --project SLUG --cover`):

```bash
# 1) upload binary; record returned JSON id, src, name, type and bytes
curl --fail-with-body -X POST 'https://maher2004.dev/api/admin/files?name=cover.webp' \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: image/webp' --data-binary @cover.webp

# 2) register returned media object using PUT /api/admin/collections/media/:id,
# then set coverMediaId on the project via PUT /api/admin/collections/projects/:slug.
```

The uploaded media must also exist in the `media` CMS collection; R2 uploads create an R2 object and an internal SQL media record, but the CMS editable media array is a separate collection. The dashboard and supplied agent helper handle this registration automatically.

The default tab icon is `/favicon.png`, generated locally with Pillow (blue rounded square + white M) without AI; an uploaded favicon/logo in Dashboard Settings overrides it.


## Web Push notifications

All endpoints below require the same admin bearer authentication as other admin APIs. See [WEB_PUSH.md](WEB_PUSH.md) for setup, browser compatibility, transport troubleshooting and encryption details. The architecture and maintenance guide is in [README.md](../README.md).

| Method | Path | Request / response |
|---|---|---|
| GET | `/api/admin/push` | `{configured,publicKey?,devices}`; each device has `id,label,created_at,active,preview` when configured. No raw endpoint or encryption secret is returned. |
| POST | `/api/admin/push/subscribe` | `{endpoint,publicKey,label,keys?}`; optional `keys: {p256dh,auth}`. Returns `{id}` with 201; 409 when five-device cap is reached. |
| POST | `/api/admin/push/devices/:id/test` | Send a generic or encrypted sample push; returns `{status,accepted,expired,reason?}`. |
| DELETE | `/api/admin/push/devices/:id` | Remove server subscription and associated encryption keys; `{ok:true}`. Browser unsubscribe is a separate client action. |

- `id` is the 64-character lowercase SHA-256 hex digest of the push endpoint. The VAPID public key must match the configured key. Only supported HTTPS provider hosts are accepted. Old-key devices still count toward the five-device limit.
- The optional encryption keys come from the browser PushSubscription; p256dh is a base64url uncompressed P-256 public key (65 bytes), and auth is a base64url 16-byte secret. Existing clients omitting keys do not clear stored preview credentials. Never fabricate keys or endpoints.
- Notification previews are encrypted using RFC 8291 / 8188 aes128gcm. Legacy devices receive a generic payload-free notification. Actual contact notifications include the sender name and a bounded 100-code-point preview; the test uses synthetic text.
- A test result with status 0 indicates a failure without a provider HTTP response. The safe reason can be invalid_endpoint, key_mismatch, signing_failed, encryption_failed, timeout or network_error. Provider rejections and redirects are reported separately (provider_rejected, redirect_rejected). Expired subscriptions (404/410) are removed. Provider acceptance does not prove device display.
- 503 indicates missing/invalid server VAPID configuration; 404 indicates a missing test device; 409 can indicate a key mismatch or capacity limit. Admin authentication and origin checks apply before these handlers.
- Push is best effort and scheduled after successful contact storage. Do not treat an accepted notification as evidence of message delivery. The inbox remains authoritative. Do not send tests or remove registrations without authorization.
- The full SQL backup can include private device endpoints and encryption credentials. Do not expose these or the separate VAPID private JWK in logs, chat or public files.
